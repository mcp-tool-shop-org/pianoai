## Lane A — MCP server production & security currency (Aug 2026)

1. **Source:** Model Context Protocol, "Key Changes" changelog, spec revision 2026-07-28 (modelcontextprotocol.io/specification/2026-07-28/changelog) · **Finding:** The current final spec revision is 2026-07-28 (RC locked 2026-05-21, finalized 2026-07-28) — two full revisions past 2025-06-18 — and it makes the protocol stateless: removes the `initialize`/`initialized` handshake, `Mcp-Session-Id`, `ping`, `logging/setLevel`, and SSE resumability; adds a mandatory `server/discover` RPC, per-request `_meta` version negotiation, and a Multi-Round-Trip-Request pattern replacing server-initiated calls. · **Implication:** Check what protocol version/handshake shape the server actually speaks — 2025-06-18-era semantics are two generations behind the wire protocol.
2. **Source:** Same changelog, "Deprecated" section · **Finding:** Roots, Sampling, and Logging are formally deprecated (12-month window), legacy HTTP+SSE transport is reclassified Deprecated, and OAuth Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents. · **Implication:** Flag any use of Roots/Sampling/Logging capabilities or HTTP+SSE as migration debt, even though still functional today.
3. **Source:** modelcontextprotocol.io, 2025-11-25 changelog · **Finding:** The intermediate revision added OIDC discovery, icons metadata, incremental scope consent via `WWW-Authenticate`, upgraded elicitation (URL-mode + richer enums), tool-calling in sampling, and Client ID Metadata Documents. · **Implication:** Auth/elicitation code should be checked against this intermediate revision, not just 2025-06-18.
4. **Source (Class A for the version numbers):** npm registry + GitHub modelcontextprotocol/typescript-sdk releases · **Finding:** Latest v1-line SDK is 1.30.0 — ahead of this repo's installed 1.29.0 — including a security fix widening the bundled `@hono/node-server` past advisory GHSA-frvp-7c67-39w9; a separate v2 package family (`@modelcontextprotocol/server`/`client`/`core`, live at 2.0.0) implements the 2026-07-28 spec and is a distinct migration decision, not a version bump. · **Implication:** Bump the v1 pin to pick up 1.30.0's fixes; treat v2 as a tracked migration decision for the Director, not a swarm auto-fix.
5. **Source:** modelcontextprotocol.io, official Security Best Practices page · **Finding:** Named attack classes with MUST/SHOULD mitigations: Confused Deputy, Token Passthrough (servers MUST NOT forward tokens not issued for them), SSRF during OAuth metadata discovery, State Handle Hijacking (new — handles replacing sessions MUST be bound server-side, never trusted as authentication), Local Server Compromise, OAuth URL scheme validation, stdio-proxy privilege escalation. · **Implication:** Check token handling and any cross-call state/handle by name against this list.
6. **Source:** OWASP, "MCP03:2025 – Tool Poisoning" (OWASP MCP Top 10, 2025); Cloud Security Alliance note (2026-07-01); MCPTox benchmark (arXiv, Aug 2025) · **Finding:** Tool poisoning — malicious/altered tool descriptions steering an agent — is a catalogued top-10 risk with real CVEs (e.g., CVE-2025-54136); the protocol itself doesn't defend against it. · **Implication:** With ~50 tool descriptions, audit how tool metadata is authored/reviewed — descriptions are attack surface, not just docs.
7. **Source:** modelcontextprotocol.io, 2025-06-18 changelog · **Finding:** `outputSchema`/`structuredContent`, tool annotations (`readOnlyHint`/`idempotentHint`/`openWorldHint`/`title`), and elicitation were introduced in 2025-06-18 itself. · **Implication:** Whether the tools declare `outputSchema`/annotations is a *baseline* mid-2025 currency check, not a bleeding-edge one.
8. **Source:** GitHub modelcontextprotocol/registry, "Official Registry Server.json Requirements" · **Finding:** The official registry requires a `server.json` manifest, namespace-ownership proof, packages from trusted registries, and a matching `mcpName` in `package.json`. · **Implication:** If registry listing is a goal, `server.json`/`mcpName` presence is the check — typically absent from pre-2026 scaffolds.

## Lane B — Listening-test methodology (for the human-audio Panel)

1. **Source:** ITU-R Rec. BS.1534-3 (MUSHRA), 2015 — itu.int/dms_pubrec/itu-r/rec/bs/R-REC-BS.1534-3-201510-I!!PDF-E.pdf · **Finding:** MUSHRA mandates post-screening: reject listeners who mis-rate the hidden reference or mid-anchor on >15% of items. · **Implication:** The panel's discrimination-floor gate is a standards-recognized pattern — codify it as a numeric threshold across floor trials (e.g., fail past >15%), not single-trial pass/fail.
2. **Source:** ITU-R Rec. BS.1116-3, 2015 · **Finding:** Double-blind hidden-reference testing for trained listeners; ~20 subjects "often sufficient" under tight control. · **Implication:** ~20 listeners is the small-N sufficiency benchmark; the expert-panel machinery itself doesn't transfer to an open web panel.
3. **Source:** Varadhan et al., "Rethinking MUSHRA," TMLR 2024/25, arXiv:2411.12719 · **Finding:** 2AFC forced-choice is a recognized lower-fatigue alternative, but each binary trial carries less information, so more trials are needed for equivalent resolving power; MUSHRA suffers reference-matching bias. · **Implication:** Pairwise A/B is the right call for untrained listeners — but budget more total votes than a rating design would need.
4. **Source:** Hoeg et al., EBU Technical Review 274 (BS.1116-derived) — tech.ebu.ch/docs/techreview/trev_274-hoeg.pdf · **Finding:** Formal practice level-aligns stimuli (to ~0.1 dB) because listeners are biased toward the louder of two clips. · **Implication:** **The panel must loudness-match A and B before playback** (LUFS or RMS alignment) or a merely-louder voicing wins for the wrong reason and contaminates the Bradley-Terry fit.
5. **Source:** Lechler, Moradi & Balić, Interspeech 2025, arXiv:2506.00950 · **Finding:** ICC > 0.99 test-retest reliability at ~15 ratings/item (Prolific) vs ~25 (MTurk) — required volume is population-dependent. · **Implication:** Budget ≥15–25 votes per system-pair-per-song before trusting a win rate; re-verify against the panel's own retest data.
6. **Source:** Levtsov & Ustalov, arXiv:2507.01633, 2025 · **Finding:** Stable Bradley-Terry rankings (ρ≥0.90 under resampling) needed ≈12·m·log(m) judgments per pair — for m=4, ≈66/pair, ~400 total. · **Implication:** At k=4 systems, target hundreds of total votes before publishing a ranking; bootstrap the CI (resample + refit), never a bare point estimate. (The shipped `bws.ts` already bootstraps — keep that.)
7. **Source:** Schoeffler et al., webMUSHRA, JORS 2018; Barry et al., Go Listen, JORS 2021 (doi.org/10.5334/jors.361); Kraft & Zölzer, BeaqleJS (github.com/HSU-ANT/beaqlejs) · **Finding:** All three frameworks standardize: Web-Audio playback, per-listener randomized trial/condition order, trial config as declarative data separate from player UI, hidden anchor/reference injection among real trials. · **Implication:** Build the panel's trial list (song × system-pair × floor-trial) as declarative data with per-listener randomization — never hardcode sequence in UI logic.
8. **Source:** Schinkel-Bielefeld et al., Proc. Meetings on Acoustics 19, 2013 · **Finding:** Expert listeners are measurably more reliable than naive ones; naive rankings track experts' mainly on larger differences. · **Implication:** One trained ear screens obviously-broken voicings; a published close-quality ranking still needs the multi-listener panel. (Adjacent evidence only — the direct single-listener-predicts-panel question was **not found**.)

## Lane C — Web Audio engineering + DAW accessibility

1. **Source:** Chrome for Developers "Autoplay policy in Chrome"; MDN "Web Audio API best practices"; WebKit blog 7734 · **Finding:** All engines require creating/resuming the AudioContext inside a user gesture; Safari layers a per-site autoplay permission on top. · **Implication:** Verify the cockpit's AudioContext is created/resumed strictly inside a gesture handler; test first-sound in Safari specifically.
2. **Source:** Chris Wilson, "A Tale of Two Clocks," web.dev/articles/audio-scheduling (2013, still MDN-linked) · **Finding:** Accurate playback needs a lookahead scheduler (~25ms timer loop scheduling ~100ms ahead on `AudioContext.currentTime`), never sound fired straight from a JS timer. · **Implication:** Check the transport/piano-roll scheduling for the lookahead shape.
3. **Source:** MDN, "BaseAudioContext.currentTime" · **Finding:** Post-Spectre, Firefox rounds `currentTime` to 2ms steps (100ms+ under resistFingerprinting); other engines apply comparable jitter. · **Implication:** Confirm the scheduler's lookahead window absorbs this rounding.
4. **Source:** W3C Web Audio GitHub issue #2398; MDN `decodeAudioData`; Paul Adenot, web-audio-perf notes · **Finding:** `decodeAudioData` always resamples to the context rate; Chromium/WebKit use linear interpolation on `AudioBufferSourceNode` playback with no app-level quality control. · **Implication:** Check the Concert Grand samples' native rate against the context `sampleRate` (avoid linear-interpolation artifacts on pitched notes) and whether `latencyHint: "interactive"` is set. *(Medium confidence — spec-discussion + practitioner notes, not normative.)*
5. **Source:** W3C WAI-ARIA APG, Grid and Slider patterns · **Finding:** A 2D note surface should expose grid semantics with roving tabindex + arrow/Home/End navigation; continuous controls need `role="slider"` with keyboard steps. · **Implication:** Check whether the piano-roll is keyboard-navigable/editable (not mouse-only) and whether transport/mixer controls carry slider semantics.
6. **Source:** W3C WCAG 2.2 — SC 2.5.8 Target Size (min 24×24px), SC 2.4.11 Focus Not Obscured; WCAG 1.4.2 Audio Control (Level A) · **Finding:** Interactive targets ≥24×24px; focus never fully hidden under sticky UI; audio auto-playing >3s needs a reachable pause/stop. · **Implication:** Measure note/toolbar hit-targets, verify focus survives the sticky transport bar, and require an accessible pause on any Panel auto-play.
7. **Source:** Karpodini et al., IJHCI 2025, DOI 10.1080/10447318.2025.2464899 · **Finding:** Interviews with 19 blind/visually-impaired producers: screen-reader DAW navigation is slow and visual-only feedback (meters, curves) has no accessible equivalent in mainstream tools. · **Implication:** Check for non-visual equivalents of visual-only state (velocity color, meters, A/B panel status), not just keyboard reachability.
8. **Source:** MixTester; FunkyABX (production browser A/B tools) · **Finding:** Established A/B UX: preload every track into buffers, switch at the identical sample position from one shared playhead, number-key select + spacebar play/pause. · **Implication:** The Panel must preload both A/B sources and swap at a matched transport position (not restart-from-zero), with keyboard shortcuts. *(Medium confidence — product/forum sources, not a formal study.)*
